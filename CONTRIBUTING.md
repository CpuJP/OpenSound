# Contributing to OpenSound

Thanks for your interest in improving OpenSound. Bug reports, device reports, translations and code are all welcome.

## Ground rules

- **Never commit proprietary material.** Do not add third-party proprietary software, code derived from it, firmware or third-party assets, not even in an issue or pull request. Describe protocol findings in your own words, as byte layouts, in [docs/PROTOCOL.md](docs/PROTOCOL.md).
- Be respectful. This project follows the [Code of Conduct](CODE_OF_CONDUCT.md).
- By contributing, you agree that your contribution is licensed under the GPL-3.0-or-later.

## Reporting a bug

Open an issue using the bug report template, and include:

- headphone model and firmware version (shown in the app under *Sistema*);
- distribution, GNOME version and how you installed OpenSound;
- the daemon log: `journalctl --user -u opensound -n 100`.

## Supporting a new model

Other headphones from the same family may use the same protocol with different capabilities. If you own one, open an issue with:

- the model name and firmware version;
- the output of `gdbus call --session -d io.github.cpujp.OpenSound -o /io/github/cpujp/OpenSound -m io.github.cpujp.OpenSound.GetState`.

## Development setup

```sh
git clone https://github.com/CpuJP/OpenSound.git
cd OpenSound
python3 -m unittest discover -s tests -t .
```

Code layout:

| Path | Content |
|---|---|
| `opensound/transport.py` | SDP lookup, RFCOMM link, framing, ACK handling |
| `opensound/protocol.py` | Request builders and reply parsers (no I/O) |
| `opensound/daemon.py` | D-Bus service that owns the link |
| `opensound/app.py` | GTK 4 / libadwaita app |
| `gnome-extension/` | GNOME Shell extension |
| `tests/` | Unit tests based on captured payloads |

## AI-assisted contributions

AI coding agents are welcome. Agent instructions live in [AGENTS.md](AGENTS.md), and [CLAUDE.md](CLAUDE.md) imports them for Claude Code. When an AI tool helped write a change:

- say so in the pull request description;
- review and understand every line yourself, because you are responsible for the contribution;
- test protocol changes on real hardware. AI-generated byte layouts are not accepted without a capture from a device.

## Pull requests

1. Keep each change focused, and match the style of the surrounding code.
2. Add or update tests in `tests/` for every protocol change. Payloads captured from real hardware are preferred.
3. Run the tests before opening the pull request.
4. Describe what you tested on real hardware, including the model and firmware.
